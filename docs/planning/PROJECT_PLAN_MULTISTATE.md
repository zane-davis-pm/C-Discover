## 1. Current state (verified against codebase)

C-Discover is a Next.js 14 static app — no backend, no auth, no runtime API calls. All data is pre-built JSON in `/public/data/` (flat, Florida-only filenames), produced by ~18 numbered Node scripts in `/scripts/pipeline/` run via `run_all.sh`. Every fetch script is hardcoded to Florida sources (EDR, FLDOE, FloridaCommerce, FL GIO) plus Census ACS.

Facts that shape the plan:

- `per_capita_income` and `total_expenditure` live in `lib/types.ts`, render via `lib/entity-fields.ts`, and are sortable/filterable (URL params included).
- `contact_tier` (1 | 2): `lib/types.ts:125`, computed in `15_apply_municipality_contacts.js`, checked in `13_validate.js`, displayed in `EntityDeepDiveModal.tsx:435`.
- **Deep dive is three layers, and the data lives in the wrong one.** Flow today: `EntityDetailModal` (card) → opens `EntityDeepDiveModal` (846-line modal, static fields only) → links to full page `app/entity/[type]/[id]` (`DeepDiveDashboard`, 561 lines). The chart-rich dataset from `21_build_deep_dive_data.js` is loaded **only by the full page** (`loadDeepDive` is imported only in `app/entity/[type]/[id]/page.tsx`). The modal never touches it. Removing the full page without porting its content would delete the tool's detailed data view. Also, no other component links to `/entity/` — the full page is reachable only via the modal.
- Compare: per-type selection buckets capped at 4 (`lib/compare.ts`), `CompareBar`/`CompareCheckbox`, payoff at `app/compare`.
- Pipeline refresh requires a terminal and `.env.local` with `CENSUS_API_KEY`; a missing key **silently** produces null municipality data (documented incident in `run_all.sh` comments).

**Architectural decision (agreed):** stay static as long as possible. Multi-state = config + data change; refresh = hosted one-click job; backend deferred until SSO is actually required. **Formalized in v2.8 (D9):** `next.config.mjs` now sets `output: 'export'`; see the v2.8 changelog entry above for the routing changes that required and `staticwebapp.config.json` for the Azure Static Web Apps hosting config.

### Phase 1.9 — Golden snapshot gate ✅ COMPLETE

After Phase 1 data regeneration, commit a checksummed snapshot of `/public/data/` (or a script that diffs regenerated output against committed data, field-by-field with tolerance rules). This is the regression harness for the Phase 3 refactor — especially important with AI-assisted coding, where silent data drift is the failure mode that's hardest to spot in review. ~1 day.

**Implementation:** `scripts/pipeline/check_snapshot.js` (`npm run pipeline:snapshot-check`). Chose the diff-against-git-history approach over a duplicated snapshot copy — `/public/data` is already committed, so git *is* the golden snapshot; no extra storage. Recursively diffs every JSON file's current content against `git show <ref>:<path>` (default ref `HEAD`), ignoring `last_updated` / `generated_at` / `retrieved_at` / `last_pipeline_run` (regenerated every run regardless of data change) and applying a 1e-9 relative numeric tolerance (float round-trip noise only). Exit 0 = no drift, 1 = drift found (field-level report printed), 2 = couldn't run the comparison (no git history / bad ref — a setup problem, not a drift finding). Also fixed: `21_build_deep_dive_data.js` was written but never wired into `run_all.sh`; added as a final step so deep-dive JSON is part of the same regenerate-then-snapshot-check cycle as everything else.

### Phase 3 — Multi-state architecture refactor (the big rock) ✅ COMPLETE

Informed by Phase 0's findings; gated by the Phase 1.9 snapshot.

**3.1 Standardized data model.** Universal fields (population, median HH income, total revenue, website, geo) vs. state-optional fields rendered only when present. Update `lib/types.ts`. Locked in from Phase 0 findings (see `/docs/states/SYNTHESIS.md`):

- `total_revenue` stays universal but **nullable**, with a `data_gaps` entry when unavailable (TX counties/munis, CO special districts).
- `total_expenditure` / `property_tax_revenue` are state-optional per entity type.
- `special_district` is **state-optional as an entity type** — v1 for non-FL states either omits it or ships with an explicit "financials unavailable" flag (CO). Florida's clean registry is the exception.
- Michigan townships are `municipality` records with `entity_subtype: "township"` (extend the existing subtype union), not a new entity type.
- `wyn_url` ships as a nullable placeholder field on every entity; **no link is rendered** until the WYN URL scheme is confirmed (D6).

**3.2 State config + namespaced data.** `/public/data/{state}/…`; `states.json` manifest; state selector (path prefix `/fl/explore` recommended over query param — cleaner for future per-state deploys); `lib/data.ts` loaders state-parameterized; regions/choropleth/map bounds from state config.

**3.3 Pipeline restructure: core vs. adapters.** Shared core (Census ACS, TIGER/Line geo, builders, validation, deep-dive-data); per-state adapters (`scripts/pipeline/states/fl/`) emitting a common intermediate format; `run_all.sh --state fl` / `--all`. Validation becomes schema-driven and **fails hard** on missing/misshapen fields — silent partial data has already caused one incident; multi-state multiplies the risk.

**3.4 Florida migrated as the first adapter state.** Regenerated Florida output must match the Phase 1.9 golden snapshot (modulo namespacing). This is the merge gate for the whole phase.

**Sequencing note for AI-assisted implementation:** this phase must land as ~5 separate PR-sized changes (types/schema → data layout + loaders → state selector/routing → pipeline core/adapter split → FL migration + snapshot verification), each independently verifiable. Do not attempt as one change.

### Phase 5 — One-button annual refresh (expectations reset)

Mechanism: GitHub Actions `workflow_dispatch` — pipeline runs per state, validates against schema + sanity bounds, opens a PR with regenerated data, redeploys on merge. `CENSUS_API_KEY` in repo secrets; missing key is a **hard CI failure**.

**Honest framing (revised):** "no engineering involvement required" is achievable for the *happy path only*. States change spreadsheet layouts, URLs, and formats between annual publications — for manual-download sources especially, some year-over-year engineering touch is likely. The design goal is therefore: (a) failures are **loud, early, and specific** (schema validation names the field and source that broke), (b) the admin assistant's runbook has a clean "forward this failure email to engineering" path, and (c) auto-fetchable sources are preferred wherever Phase 0 found them, shrinking the manual surface.

**Trigger surface (D5):** ✅ **Decided: custom Azure Static Web App trigger page.** A one-button internal page ("Run annual refresh" + last-run status/pass-fail/PR link), backed by an Azure Function that calls GitHub's `workflow_dispatch` API using a repo-scoped, Actions-only PAT stored in Azure Key Vault, gated by Entra ID login (no GitHub account needed for the admin assistant). Chosen over a raw GitHub Actions UI (too developer-facing for a non-technical admin) and a Power Automate button (faster to ship but throwaway — the SWA + Entra ID pattern doubles as the first piece of the eventual M365-SSO'd app shell already scoped in §4 Futures, rather than a one-off side tool). Scope: 1 Static Web App + 1 Function + 1 Key Vault secret + 1 Entra app registration; roughly a few days of engineering. Manual-download sources still get an "upload replacement seed file" path documented in the runbook (Phase 6). Not yet built.
